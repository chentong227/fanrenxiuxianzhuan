# 地图即行动中枢——借鉴卡拉提亚的地图玩法落地方案

> 2026-06-25。基于 `kalatiya-research.md` 调研结论 + 现有系统全面审计。
> 目标：把凡人的地图从"导航工具"升级为"玩法容器"——每一格地图都有去的原因，
> 玩家自决去哪做什么。**不新造系统，只扩展现有架构**（乘法三律）。

---

## 〇、用户裁决方向（2026-06-25 对谈补充）

> **用户原话**："能不能直接把地图做成行动主界面，只有进到如七玄门这种级别的地图
> 才有现在的行动界面？地图直接做成大陆和大陆相连，不是一个层级是一张图，
> 而是完整连在一起的，只是可以缩放，然后人物头像在上面移动，
> 自然的带上旅途窗口。合适吗？能做吗。"

**裁决**：地图不是弹窗，是**主界面**。完整连图 + 缩放 + 头像移动 + 旅途窗口自然弹出。
只有缩放到"据点级"（如七玄门/黄枫谷）才出现现有的行动按钮界面。

**本文档分两层设计**：
- **§一~三**：旅途行动面板等玩法改造（与地图 UI 无关，独立可做）
- **§七**：地图主界面化——UI 架构重构方案（本节回答"能做吗"）

## 一、现有系统审计：地图/旅途/行动全链路

### 1.1 五级舆图（已落地 v143~v149）

| 层级 | 入口 | 渲染函数 | 当前状态 |
|------|------|---------|---------|
| L1 人界 | `openAtlas("renjie")` | 区块多边形+云罩 | ✅ 已落地，天南/大晋/慕兰/乱星海四块 |
| L2 天南 | `openAtlas("tiannan")` | 国别多边形+势力叠加 | ✅ 已落地，胥国/元武国/天罗国等 |
| L3 胥国 | `openContinent()` | 水墨舆图+据点 pin+州名 | ✅ 已落地，十三州+据点+路线墨痕 |
| L4 地区 | `openTravel()` | 地点 pin+连线 | ✅ 已落地，当前节点内地点云游 |
| L5 据点 | `renderActions()` | 地点屏+行动按钮 | ✅ 已落地，按地点动态生成行动 |

**关键数据**：
- `WORLD.atlas.levels` — L1/L2 区块数据（`@/js/world.js:500`）
- `WORLD.continent.nodes` — L3 胥国据点（`@/js/world.js:394~448`）
- `WORLD.continent.routes` — 据点间路线（`@/js/world.js:449~458`）
- `WORLD.locations` — L4/L5 地点数据（`@/js/world.js:17~381`）

### 1.2 旅途系统（已落地）

**引擎**：`Engine.startJourney(nodeId)` → `_journeyLeg()` → `_journeyArrive()`
（`@/js/engine.js:2145~2221`）

**流程**：
1. 点大陆节点 → `startJourney` → 设 `s.journey = {to, leg:0, total:months}`
2. 每月走一段：`_journeyLeg()` → `passTime(1)` → 40% 概率遇事件
3. 事件池 `_JOURNEY_EVENTS`（5 个事件，`@/js/engine.js:2075~2143`）：
   - 茶棚风闻（22 权重）/ 破庙夜宿（16）/ 受伤行商（14）/ 剪径毛贼（16）/ 山坡灵草（12）
4. 事件弹出抉择卡（复用奇遇管线 `openFortune`），选完自动续走
5. 走完到达 → `_journeyArrive()` → 落脚首地点 + 触发剧情

**现状问题**：
- 旅途是**被动读条**——玩家点"启程"后只能等事件弹出，无法主动选择"在路上做什么"
- 事件池只有 5 个通用事件，无地区差异、无地形差异
- 旅途和地点行动完全割裂——旅途途中不能采药/探索/扎营，只有预设事件

### 1.3 地点行动系统（已落地）

**引擎**：`Engine.doAction(action)` → 按地点 `loc.actions` 生成按钮
（`@/js/ui.js:715~762`）

**现状**：每个地点有固定的 `actions` 列表（如药庐=`["cultivate","breakthrough","rest","bottle","alchemy"]`），
行动按钮按地点动态生成。地点之间通过 `openTravel()`（L4 云游）切换。

**现状问题**：
- L4 云游只是"选目的地→读条到达"（`travelTo`），**旅途途中无事可做**
- L3 大陆节点点击只能"启程"（`startJourney`），到达后才能行动
- **地图和行动是分离的两层**——地图只管导航，行动只管地点内

### 1.4 遭遇/探索系统（已落地）

- `adventure()` — 按地点 `loc.encounters` 表随机抽取（`@/js/engine.js:2810~2884`）
- `enterHoushan()` — 箱庭走格子（`exploreSite`）
- 遭遇表按地点定制（后山=灵草/野兽/同门；集镇=商贩/暗器/传闻/匪类）

## 二、卡拉提亚核心启发 vs 凡人现状差距

| 卡拉提亚做法 | 凡人现状 | 差距 |
|-------------|---------|------|
| 出城=扎营搜寻打怪（主动选） | 旅途=被动等事件弹出 | **旅途途中无主动行动** |
| 城间=跑商路线（有经济行为） | 城间=纯赶路（无经济行为） | **旅途无经济活动** |
| 区域分功能（山地/森林/海域） | 地点分功能（药庐/后山/集镇） | **旅途路线无地形功能** |
| 区域等级自然筛选（走错被秒杀） | 旅途险度标注（低/中/高）但无实际后果 | **险度只是文字标注** |
| 飞艇=挣来的快速传送 | 飞行法宝=旅途月数折减 | **已覆盖（更优）** |

**核心差距一句话**：凡人的旅途是"点目的地→等→到达"，卡拉提亚的旅途是
"在路上可以主动做很多事"。**凡人的旅途事件池设计对了，但交互模式错了——
是被动弹窗而不是主动选择。**

## 三、落地方案：把旅途从"读条"变成"行动中枢"

### 3.1 核心改造：旅途途中可主动行动

**改造点**：旅途走段时，不只弹随机事件，而是给玩家一个**旅途行动面板**。

**当前流程**：
```
startJourney → _journeyLeg (passTime 1) → 40% 弹事件 / 60% 平安 → 自动续走
```

**改造后流程**：
```
startJourney → _journeyLeg (passTime 1) → 弹出"旅途行动面板"：
  ┌─────────────────────────────────────┐
  │  第 2 月 · 赴黄枫谷途中（共 3 月）    │
  │  当前地形：太岳山脉·山道              │
  │                                     │
  │  ○ 赶路（平安推进，可能遇事件）       │
  │  ○ 扎营搜寻（消耗1月，可能发现灵草/   │
  │    遭遇妖兽/发现古洞）               │
  │  ○ 打听风闻（消耗1月，获市井传闻）    │
  │  ○ 跟随商队（省半月路程，可能遇劫）   │
  │  ○ 采药（消耗1月，按地形产灵草）      │
  └─────────────────────────────────────┘
```

**设计要点**：
1. **"赶路"=默认选项**：选了就推进 1 月，40% 概率遇事件（同现有逻辑）
2. **"扎营搜寻"=主动探索**：消耗 1 月，按地形抽遭遇（复用 `adventure()` 遭遇表）
3. **"打听风闻"=信息收集**：消耗 1 月，获传闻/情报（复用 `_AMBIENT_EVENTS`）
4. **"跟随商队"=跑商雏形**：省 0.5 月路程，但 20% 概率遇劫（战斗或破财）
5. **"采药"=旅途采集**：消耗 1 月，按地形产灵草（复用 `gather` 逻辑）
6. **每个选项都有月数消耗**——选了就 `passTime`，旅途总月数不变（只是路上多花了时间）
7. **旅途月数用完自动到达**——`leg >= total` 时触发 `_journeyArrive()`

**乘法审计**：
- 不是新系统——旅途面板=旅途事件池的"主动版"（从被动弹窗变成主动选择）
- 遭遇表复用 `loc.encounters` + `_JOURNEY_EVENTS`
- 采药/打听/搜寻复用现有 `adventure()` / `_AMBIENT_EVENTS` / `gather` 逻辑
- UI 复用 `openFortune` 管线（只是 choices 变成旅途行动）

### 3.2 地形功能化（旅途路线分地形）

**改造点**：`WORLD.continent.routes` 加 `terrain` 字段，不同地形有不同的旅途行动/遭遇。

**数据改造**（`@/js/world.js:449~458`）：
```js
routes: [
  { from: "caixia", to: "qingniu", terrain: "hill" },      // 山道
  { from: "caixia", to: "huangfeng", terrain: "mountain" }, // 深山
  { from: "qingniu", to: "yuejing", terrain: "plain" },     // 平原官道
  { from: "yuejing", to: "jiayuan", terrain: "plain" },     // 平原官道
  { from: "jiayuan", to: "tainangu", terrain: "forest" },   // 山林
  { from: "huangfeng", to: "yuanwu", terrain: "mountain" }, // 深山
  ...
]
```

**地形效果表**：

| 地形 | 采药产出 | 搜寻遭遇 | 特殊行动 | 险度 |
|------|---------|---------|---------|------|
| `plain` 平原 | 灵草×1 | 商贩/传闻/匪类 | 跟随商队 | 低 |
| `hill` 丘陵 | 灵草×2 | 野兽/散修/灵草 | 扎营搜寻 | 中 |
| `mountain` 深山 | 灵草×2+毒草 | 妖兽/古洞/险地 | 攀险径（省时但危险） | 高 |
| `forest` 山林 | 灵草×2+灵木 | 妖兽/同路散修 | 狩猎（获肉材） | 中 |
| `water` 水域 | 无 | 海妖/风浪 | 渡水（需飞行法宝） | 高 |

**乘法审计**：只给 routes 加一个 `terrain` 字段，旅途行动面板按 terrain 调整可选项和遭遇池。
不改地点数据、不改遭遇表结构。

### 3.3 旅途险度实化（危险区域有实际后果）

**当前**：`node.danger` 只是文字标注（低/中/高），无实际影响。

**改造**：
1. **低险度路线**：事件概率 30%，事件池偏温和（风闻/灵草/行商）
2. **中险度路线**：事件概率 40%，事件池混合（匪类/妖兽/灵草/古洞）
3. **高险度路线**：事件概率 55%，事件池偏危险（妖兽/散修劫道/险地），
   但**收益也高**（稀有灵草/古洞遗物/强敌掉落）
4. **境界门槛自然筛选**：练气一层走 3 月深山路去黄枫谷=路上可能遇筑基级妖兽
   （打不过就死/重伤/破财逃）——**看得见去不了=变强动机**（world-architecture §1.2 铁律 1）

**乘法审计**：只调 `_journeyLeg` 的事件概率和池过滤，加境界对照。
不改数据结构、不改战斗系统。

### 3.4 轻量跑商（坊市地区差价）

**改造点**：给 `WORLD.locations` 中有坊市的地点加 `marketGoods` 字段，实现地区差价。

**数据改造**：
```js
// 药庐/集镇/嘉元城/黄枫谷坊市/太南小会 各有不同的市价表
{
  id: "town",
  marketGoods: {
    lingcao:   { base: 3,  range: [2, 5]  },   // 灵草：山下集镇便宜
    duyao_cao: { base: 8,  range: [5, 12] },
    anqi:      { base: 5,  range: [3, 8]  },
  },
  // 价格按月份波动：每月 random(base * 0.65 ~ base * 1.55)
}
{
  id: "fangshi",
  marketGoods: {
    lingcao:   { base: 6,  range: [4, 9]  },   // 黄枫谷坊市灵草贵（修仙者需求大）
    duyao_cao: { base: 15, range: [10, 22] },
    // 灵石交易：灵石↔纹银兑换率也随地点变
  },
}
```

**玩法**：
1. 在 A 地买灵草（3 两）→ 跟商队/赶路到 B 地卖（6 两）= 赚差价
2. 价格每月波动（存 `s.marketPrices`，`passTime` 时刷新）
3. 太南小会的修仙者集市有特殊商品（丹药/法器/灵石兑换），价格更高但货源独特
4. **不做负重/载具/粮食**——只有"价目表+波动+差价"三要素

**乘法审计**：
- 复用现有 `openMarket()` / `openFair()` UI
- 复用 `passTime` 的月份推进做价格刷新
- 只加 `marketGoods` 字段 + 价格波动逻辑，不改交易 UI 结构
- 跑商收入受限于旅途月数（你不能无限来回跑，月数就是成本）

### 3.5 精英妖兽词缀（非剧情遭遇变化度）

**改造点**：`startEncounterFight` 生成敌人时，有概率附加词缀。

**词缀池**（轻量版，6 个）：
```js
_ENC_AFFIXES: [
  { id: "fierce",  name: "凶残",  desc: "伤害大幅增加",     apply: e => e.atk = (e.atk||10) * 1.5 },
  { id: "tough",   name: "坚韧",  desc: "双防增加",         apply: e => { e.def = (e.def||0) + 5; e.mdef = (e.mdef||0) + 5; } },
  { id: "swift",   name: "迅捷",  desc: "攻速增加",         apply: e => e.spd = (e.spd||10) * 1.3 },
  { id: "venom",   name: "剧毒",  desc: "攻击附带毒",       apply: e => e.poison = true },
  { id: "vital",   name: "健壮",  desc: "生命大幅增加",     apply: e => e.hp = Math.round(e.hp * 1.6) },
  { id: "savage",  name: "嗜血",  desc: "攻击回血",         apply: e => e.lifesteal = 0.3 },
]
```

**规则**：
1. **只加在非剧情遭遇**（`adventure()` 抽到的 fight + 旅途扎营搜寻遭遇）
2. 剧情Boss（墨大夫/金光/王蝉）**不加词缀**——全定制
3. 概率：20% 概率 1 个词缀，5% 概率 2 个词缀
4. **高探知=提前看到词缀**：`s.skills.scouting >= N` 时在战斗前显示"这只妖兽气息异常——[凶残]"
5. **词缀让杂学更有用**（探知/药理/剑意有更多用武之地）

**乘法审计**：
- 只在 `startEncounterFight` 加词缀修饰器
- 词缀效果复用现有战斗属性（atk/def/hp/poison/lifesteal）
- 不改战斗引擎核心、不改剧情 Boss

### 3.6 摸鱼碎片入口（灵圃快捷入口+现实时间小 buff）

**改造点 A**：主界面加"今日灵圃"快捷按钮（已有小绿瓶入口，只需在顶栏常驻）。
**改造点 B**：读 `new Date()` 做小 buff：
- 夜晚（22~5 时）玩=灵圃夜露加成（催熟进度 +10%）
- 雨天玩=灵气微涨（修炼效率 +5%）

**落地成本**：极低。灵圃系统已有，只需加快捷入口 + 读时间做 buff。

## 五、改造后的玩家体验流程

### 改造前
```
点"远眺天下" → 看大陆图 → 点黄枫谷 → "启程" → 等3月弹窗 → 到达
  （旅途中只能看弹窗选选项，无事可做）
```

### 改造后
```
点"远眺天下" → 看大陆图 → 点黄枫谷 → 看到险度"高·深山" → "启程"
  → 第1月：旅途面板弹出
     → 选"赶路" → 平安推进
  → 第2月：旅途面板弹出
     → 选"扎营搜寻" → 遇到一头妖狼（词缀：凶残）→ 战斗 → 胜
  → 第3月：旅途面板弹出
     → 选"采药" → 在太岳山脉采得灵草×2 + 毒草×1
  → 到达黄枫谷 → 落脚外门居所
```

**体验变化**：
- 旅途从"等待"变成"决策"——每月都有事做、有选择
- 地形有意义——山道采药和平原赶路的体验完全不同
- 险度有后果——高险度路线收益高但危险，低险度安全但平庸
- 玩家有自决权——可以一路赶路快速到达，也可以沿途探索慢慢走

## 七、地图主界面化——UI 架构重构方案

> 回答用户问题："能做吗？合适吗？"
> **结论：能做，且非常适合手机端。但这是 UI 架构级重构，需要分阶段实施。**

### 7.1 当前 UI 架构 vs 目标架构

**当前架构**（`@/index.html:100~218`）：
```
screen-game
  ├─ scene-stage（全屏场景图做底）
  │   ├─ scene-bg / scene-far / scene-fg（2.5D 场景层）
  │   ├─ scene-pins（场景内可点击元素）
  │   └─ locals（在场人物立绘）
  ├─ topbar（顶栏：时间 + 舆图/小瓶/人物等按钮）
  ├─ layout（HUD 三栏 grid）
  │   ├─ side-rail（左：角色卡 + 状态条 + 储物袋）
  │   ├─ mid-col（中下：目标 + 最近日志 + 行动按钮）
  │   └─ stage-col（右：见闻叙事 + 抉择）
  └─ mobile-tabs（手机底栏：见闻/行动/韩立）
```

地图是**弹窗**（`openAtlas`/`openContinent`/`openTravel` → `openModal`），
与主界面完全分离。

**目标架构**：
```
screen-game
  ├─ worldmap-canvas（全屏可缩放地图做底——替代 scene-stage）
  │   ├─ SVG 层：区块多边形 + 路线 + 据点 pin（复用现有 atlas 数据）
  │   ├─ avatar-pin（韩立头像，在地图上移动）
  │   └─ 缩放/平移控制（viewBox 操控）
  ├─ topbar（顶栏：保留，精简）
  ├─ hud-overlay（浮在地图上的 HUD——替代 layout grid）
  │   ├─ 角色卡（可折叠浮窗）
  │   ├─ 见闻日志（可折叠浮窗/底部 sheet）
  │   └─ action-dock（据点级缩放时滑出的行动面板）
  └─ mobile-tabs（手机底栏：保留，但"行动"=地图/行动 dock）
```

**核心变化**：
1. `scene-stage`（静态场景图）→ `worldmap-canvas`（可缩放地图）
2. `layout`（三栏 grid）→ `hud-overlay`（浮窗/dock）
3. 地图从弹窗变成主界面
4. 缩放级别替代层级弹窗：缩放越深=看得越细=从大陆到据点

### 7.2 缩放级别与数据映射

**关键洞察**：现有五级数据（L1~L5）天然对应五个缩放级别，
不需要重新建模——只需要一个统一的坐标变换系统。

| 缩放级别 | 可见内容 | 数据源 | 当前对应 |
|---------|---------|--------|---------|
| Z1 最远 | 人界全图：天南/大晋/慕兰/乱星海四块 | `WORLD.atlas.levels.renjjie` | L1 `openAtlas("renjie")` |
| Z2 远 | 大区图：天南各国 | `WORLD.atlas.levels.tiannan` | L2 `openAtlas("tiannan")` |
| Z3 中 | 国别图：胥国十三州据点+路线 | `WORLD.continent` | L3 `openContinent()` |
| Z4 近 | 地区图：当前据点内地点 | `WORLD.locations` (当前 node locs) | L4 `openTravel()` |
| Z5 最近 | 据点行动：场景图+行动按钮 | `loc.actions` + scene | L5 `renderActions()` |

**坐标统一**：所有层级的节点都有 `pos:{x,y}`（0~100 坐标空间）。
缩放 = 调整 SVG viewBox 的 min-x/min-y/width/height：
- Z1：viewBox = `0 0 100 100`（看全部）
- Z3：viewBox = 胥国区块范围（如 `10 5 70 80`，只看胥国）
- Z5：viewBox = 当前据点位置附近（如 `15 17 8 8`，只看彩霞山周边）

**实现方式**：SVG `viewBox` 属性 + CSS `transition` 做平滑缩放动画。
不需要 Canvas/WebGL——现有 SVG 渲染直接复用。

### 7.3 头像移动

**avatar-pin**：一个绝对定位的 div，`left/top` 按 `pos` 百分比设定。

**静止时**：头像停在当前所在据点的 `pos` 位置。

**旅途时**（`s.journey` 存在）：
1. 计算路线：`from 节点 pos` → `to 节点 pos`（直线插值，或沿 routes 路径）
2. 每月走段时（`_journeyLeg`），头像沿路线移动 `1/total` 的距离
3. CSS `transition: left 2s, top 2s` 做平滑移动动画
4. 移动过程中旅途行动面板自动弹出（§三的旅途面板）
5. 到达时头像停在目标节点位置

**路线插值**：
```js
// 简单版：直线插值
const from = currentNode.pos, to = targetNode.pos;
const progress = j.leg / j.total;  // 0→1
const ax = from.x + (to.x - from.x) * progress;
const ay = from.y + (to.y - from.y) * progress;
```

### 7.4 据点级行动面板

**触发条件**：缩放到 Z5（viewBox 聚焦到某个据点位置附近）且该据点已到达。

**UI 呈现**：
- 地图缩小为上半屏背景（或渐隐为场景图）
- 下半屏滑出行动 dock（复用现有 `renderActions()` 逻辑）
- 手机端：底部 sheet 上滑，露出行动按钮列表
- 桌面端：底部居中 dock 浮窗

**场景图过渡**：
- Z4→Z5 缩放时，地图淡出、场景图淡入（CSS opacity transition）
- Z5→Z4 缩小回时，场景图淡出、地图淡入
- 复用现有 `Env.apply()` 场景系统——只是触发方式从"点地点"变成"缩放到据点"

### 7.5 HUD 浮窗化

现有三栏 grid（side-rail/mid-col/stage-col）改为浮在地图上的可折叠面板：

**手机端**（430×932）：
- 顶栏：保留（时间 + 菜单按钮）
- 地图：全屏可见（主界面）
- 底部 sheet：见闻日志（可上滑展开）/ 行动 dock（据点级出现）
- 底栏 tab：见闻 / 地图 / 韩立（"行动"并入地图）

**桌面端**（>1180px）：

### 7.8 风险与对策

| 风险 | 对策 |
|------|------|
| **手机 SVG 性能** | 按 zoom 级别只渲染可见节点（Z1 只画 4 块大区，Z3 才画据点 pin） |
| **坐标空间不一致** | L1/L2 的 poly 坐标和 L3 的 pos 坐标都在 0~100 空间，但语义不同——需统一变换矩阵 |
| **场景图与地图的切换突兀** | 用 CSS opacity transition 做交叉淡入淡出，不硬切 |
| **现有弹窗逻辑冲突** | `openModal` 管线保留（奇遇/剧情/战斗仍用弹窗），地图不再是弹窗 |
| **存档兼容** | 不改 state schema——地图缩放级别是 UI 状态，不存档（重开默认 Z3 当前所在国） |
| **回归测试** | `test/journey.test.js` 旅途测试不受影响（只测引擎逻辑，不测 UI） |

### 7.9 与 §三旅途面板的关系

§三的旅途行动面板和 §七的地图主界面化是**互补**的：
- §三改造旅途的**内容**（旅途中可做什么）
- §七改造旅途的**呈现**（头像在地图上移动 + 面板自然弹出）

**可以独立实施**：先做 §三（旅途面板，不改 UI 架构），再做 §七（地图主界面化）。
也可以合并做：地图主界面化时直接把旅途面板作为旅途途中的弹出层。

### 7.10 结论

**合适吗？** 非常合适——
- 手机端全屏地图 + 底部 sheet 是最自然的移动端布局
- "缩放看天下"比"点弹窗翻层级"沉浸感强一个量级
- 头像在地图上移动 = 旅途的视觉化（比文字日志"你走了 3 月"直观百倍）
- 与卡拉提亚的"地图即玩法容器"哲学完全对齐

**能做吗？** 能做——
- 数据层零改动（atlas/continent/locations 不变）
- 渲染层复用现有 SVG 逻辑（viewBox 操控 + pin 渲染）
- 核心工作量在 UI 布局重构（index.html + style.css + ui.js）

**工程量**：大（UI 架构级重构），但可分 5 阶段渐进实施，每阶段独立可验收。
建议先落地 §三旅途面板（低风险高收益），再做 §七地图主界面化（高收益但大工程）。
