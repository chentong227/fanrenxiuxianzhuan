# 篇章系统清单（Chapter Systems Manifest）

> **本文档是 chapter-template.md 的补充件。** chapter-template 管的是"篇章配置怎么填"，
> 本文档管的是"篇章设计时怎么让六大横轴系统同步推进"。
>
> **强制规则**：任何篇章设计文档（`docs/XX-design.md`）必须包含本文档§一所列的
> **系统推进表**，填完才可进入实装。Agent 接手篇章开发时，先读 chapter-template.md，
> 再读本文档，按模板填表。

---

## 〇、问题定义：为什么需要这份清单

游戏有两类内容：
1. **纵轴内容（随篇章推进）**：主线剧情、新地点、新NPC、新敌人——每章不同
2. **横轴系统（跨篇章持续）**：Build 三路（剑/丹/阵）、因果账本、命途道岔、探索随机——每章都要喂

纵轴靠剧情自然推动，不会被遗忘；**横轴容易被遗忘**——agent 写剧情时满脑子都是
"陈巧倩怎么救"，忘了"这个月韩立的丹道熟练度该涨了吗"。

**解法**：每章设计文档必须填一张**系统推进表**，强制 agent 对每个横轴系统回答
"本章怎么喂它"。填不出来=设计缺口，必须补。

## 一、系统推进表（每章必填，模板）

### 表 A：Build 三路推进

```
| 系统 | 本章新增内容 | 里程碑门槛 | 月行动入口 | 与主线的乘法点 |
|------|-------------|-----------|-----------|--------------|
| 剑道 | （填：新功法层/新招式/新剑形法宝） | （填：哪一层解锁什么） | （填：哪个行动按钮涨剑道） | （填：哪个剧情节点因剑道高/低而不同） |
| 丹道 | （填：新丹方/新材料/新炼丹场景） | （填：药理多少解锁什么） | （填：哪个行动按钮涨丹道） | （填：哪个剧情节点因丹道高/低而不同） |
| 阵法 | （填：新符箓方案/新阵旗/新布阵场景） | （填：阵法多少解锁什么） | （填：哪个行动按钮涨阵法） | （填：哪个剧情节点因阵法高/低而不同） |
```

**填写规则**：
- "本章新增内容"至少一项（哪怕是"本章无新增，沿用上章"也要写明）
- "月行动入口"必须指向具体的行动按钮名（如"采药""炼药""制符"），不可空
- "与主线的乘法点"至少一个（剧情节点因 build 高低而产生不同演出/难度/选项）
- 如果某路在本章确实没有推进空间（如阵法在七玄门篇），写"本章不开轴，理由：考据红线（辛如音赠物在再别天南）"

### 表 B：因果账本（种因 / 收果）

```
| 种因（本章埋下） | 写入 ledger 的 key | 近响（当场可见） | 远雷（哪一章兑现） |
|-----------------|-------------------|----------------|------------------|
| （填：玩家做了什么选择） | （填：s.ledger.xxx） | （填：当场的小后果） | （填：在哪个后续节点读这条 ledger 改变演出） |
```

**填写规则**：
- 每章至少 2 条种因（玩家选择写入账本）
- 每章至少 1 条收果（读取之前章节埋的 ledger，改变本章某个节点的演出）
- 首章（七玄门）只种不收；后续章必须有收
- **远雷必须指名**：写清楚"在 XX 篇的 YY 节点兑现"——不可写"未来某处"
- 种因的 ledger key 命名规范：`动词_对象`（如 `saved_chenqiaoqian`、`spared_modao_spy`）

### 表 C：命途道岔

```
| NPC | 本章道岔 | 窗口（日历锚） | 代价 | 默认走向（不动手） | 转机走向（动手） |
|-----|---------|--------------|------|------------------|----------------|
| （填：哪个NPC） | （填：道岔 id） | （填：什么时间窗口） | （填：花什么资源） | （填：原著结局） | （填：改变后的结局） |
```

**填写规则**：
- 参照 fate-design.md 已有的 NPC 命途表
- 道岔的代价必须吃 Build 三路的资源池（药材/时间/灵石）——确保道岔与 build 资源竞争
- 窗口必须是具体的日历锚，不可"随时可做"
- 不在本章出现的 NPC 不用填

### 表 D：时间窗口互斥

```
| 窗口期 | 互斥事件 A | 互斥事件 B | 互斥事件 C（可选） | 错过补救径 |
|--------|-----------|-----------|------------------|-----------|
| （填：第 N 年 X 季） | （填：事件名+收益） | （填：事件名+收益） | | （填：错过后 skipIf 走什么补救） |
```

**填写规则**：
- 每章至少 1 组互斥窗口（驻地章 2~3 组，事件章可以 1 组）
- 互斥事件的收益必须各有所值（不可有明显最优解）
- 补救径必须存在（fail-forward：错过不卡死，但更难/更贵）

### 表 E：探索随机化

```
| 随机源 | 本章新增内容 | 权重/概率 | 对 build 的影响 |
|--------|-------------|----------|----------------|
| 奇遇事件 | （填：新增哪些奇遇） | （填：触发概率） | （填：奇遇产出影响哪条 build 路） |
| 市集刷新 | （填：本章坊市的随机商品池） | （填：刷新规则） | （填：随机商品如何影响 build 选择） |
| 遭遇表 | （填：本章新增遭遇类型） | （填：权重分配） | |
```

## 二、平衡审计（实装后必做）

> 平衡框架全文见 **build-balance-design.md**。本节是篇章维度的审计清单。

### 2.1 时间预算审计

每章实装完成后，跑一次**时间预算模拟**：

```
本章总可用月数：N 个月
├── 主线剧情消耗：约 X 月（不可省）
├── 剩余自由月数：约 Y 月
│   ├── 纯修炼（涨修为）：玩家至少需要 A 月才能突破
│   ├── 剑道推进：推 1 层约 B 月
│   ├── 丹道推进：涨 10 点约 C 月
│   └── 阵法推进：涨 10 点约 D 月
└── 验证：Y 月够深耕一条路 + 浅尝另一条，但不够全精通
```

**红线**：如果自由月数足够同时把三条路都推满 → 时间压力不存在 → build 分化失效 → **必须收紧**（加主线消耗/提高推进成本/增加窗口互斥）。

### 2.2 因果链完整性审计

```
检查项：
□ 本章每条种因都有指名的远雷目标章节
□ 本章应兑现的上章种因全部有对应的 story 节点读 ledger
□ 因果账本的 key 在 story.js 中被至少一个后续节点的 cond 引用
□ 远雷兑现时有"点名出处"台词（"多亏当日你在官道上……"）
□ 年表自动记因果对（种因时一行，结果时一行，互相链接）
```

### 2.3 乘法审计（复用 multiply-design 四问）

```
检查项：
□ 本章每个新系统/新玩法是否能用已有系统相乘得到？
□ 剑/丹/阵三路是否与本章的至少一个主线节点产生乘法？
□ 因果账本是否与至少一个战斗/探索/NPC 产生乘法？
□ 有没有"孤立的新页签"——与其他系统不相乘的独立数值条？
```

### 2.4 Build 等效时间律审计（build-balance-design.md §4.1）

```
检查项：
□ 三种纯 build（剑/丹/阵）打本章最难 boss，胜率差 ≤ 10%
□ 深耕一条路的角色胜率 ≥ 全修角色（里程碑能力的价值）
□ 本章每个关键遭遇至少有 2 种 build 解法可行
□ 三条路到达第一个质变里程碑的月数在同一量级（20~30 月）
□ 如需调参，优先调月收益系数（旋钮 1），其次调内容侧发挥场景（旋钮 2）
```

## 三、Agent 工作流（篇章开发的标准流程）

```
1. 读 AGENTS.md（红线 + 工程惯例）
2. 读 chapter-template.md（篇章配置怎么填）
3. 读本文档（系统推进表怎么填）
4. 读 build-balance-design.md（剑丹阵平衡框架）
5. 读目标篇章的 lore 文档（考据节点）
6. 读 fate-design.md（命途线当前状态）
7. 读 world-architecture.md §3（因果账本规则）
   ─── 以上为"读"，以下为"写" ───
8. 写篇章设计文档（docs/XX-design.md），内含：
   a. 动漫考据节点表（已有模板）
   b. 章节结构（已有模板）
   c. ★ 系统推进表 A~E（本文档模板）
   d. ★ Build 三路解法表（每个关键遭遇的剑/丹/阵三种打法）
   e. 大件链（已有模板）
   f. 实装切片（已有模板）
9. 系统推进表 + 解法表全部填完 → 开始实装
10. 实装完成 → 跑平衡审计（§二，含 §2.4 等效时间律）
11. 审计通过 → 提交
```

**第 8c/8d 步是新增的强制步骤**。如果 agent 跳过直接写剧情，reviewer 应打回。

## 五、系统数据结构预留（给 engine.js / state.js）

以下字段需要在 state 中预留（惰性初始化，免动 _migrate）：

```js
// Build 三路（已有两条，阵法待加）
s.skills = s.skills || { alchemy: 0, scouting: 0, formation: 0 };

// 因果账本（已有 s.flags 做雏形，升级为独立字段）
s.ledger = s.ledger || {};

// 功法层（已有）
s.techLayers = s.techLayers || {};
```

**命名规范**：
- `s.skills.alchemy` = 丹道（药理熟练度）
- `s.skills.scouting` = 探知熟练度
- `s.skills.formation` = 阵法熟练度
- `s.techLayers[techId]` = 功法层数（剑道主载体）
- `s.ledger[key]` = 因果账本条目（`true` 或数值）

## 六、写入 AGENTS.md 的摘要（供 agent 速查）

> 以下内容应追加到 AGENTS.md §三 设计哲学速记：
>
> - **系统推进清单**：每章设计文档必须包含 chapter-systems-manifest.md 定义的

> - **Build 三路平衡**：剑道/丹道/阵法的完整定义、能力表、平衡框架见 build-balance-design.md。
>   三条路填战力公式的不同格子（乘区/底牌/控场），用等效时间律校准。每章关键遭遇必须
>   有 ≥2 种 build 解法可行。蒙特卡洛校验见 test/build.bal.js。
